# LifeLine / RaktSetu — Agent Rules

Explainable blood donor–recipient matching platform. College mini project + IEEE student-conference paper. **Synthetic data only. No real donor/hospital data, ever.**

Read this file and `docs/SRS.md` at the start of every session. Implement by SRS requirement ID. If a task conflicts with this file or the SRS, STOP and ask.

## 1. Locked decisions (never change without explicit human approval)

- Stack: Java 21, Spring Boot 3.x, Spring Security, JWT + RBAC, React, PostgreSQL, Flyway.
- Matching engine is a **custom Java implementation**. No matching/optimization library inside `lifeline-core`.
- Selection algorithm: **greedy Top-N**. No Hungarian/max-weight solver in the product.
- Roles: `DONOR`, `BANK_STAFF`, `ADMIN`. There is **no RECIPIENT account**. Families/recipients use an unauthenticated public intake form -> request lands in `PENDING_REVIEW` -> staff review.
- Rarity is a **soft, configurable** ranking term, never a hardcoded rule.
- Compatibility (ABO/Rh, 8x8 table) is a **hard filter**, not a weight.
- **Cooldown is a hard exclusion**: 90 days since last donation for men, 120 days for women (donor `sex` is used ONLY to choose the interval). Donors inside the window are never ranked until it ends. Cooldown is not a ranking factor.
- Urgency selects a weight profile (it is not an additive per-donor term). The responsiveness factor is an optional toggle, OFF in the locked-spec engine.
- Every ranked match must be traceable to the factors that produced it (explainability is a core contribution).
- Unregistered-donor outreach (WhatsApp/Instagram) is future scope. Do not build it.
- The clinical caveat must appear in the README and UI: the system routes/ranks only; final clinical eligibility and cross-matching belong to qualified blood-bank staff.

## 2. Module layout and dependency rule

| Module | Purpose | May depend on |
|---|---|---|
| `lifeline-core` | Domain, compatibility, filter, factors, ranker, explanations, fallback, Tier-0. Pure Java, no Spring. | nothing |
| `lifeline-sim` | Synthetic world, latent donor traits, response models, ground truth. | core (domain types only) |
| `lifeline-eval` | Baselines, experiment runner, metrics, CSV output, demo-data export. | core, sim |
| `lifeline-api` | Spring Boot API, JWT/RBAC, DB, NLP intake. | core |
| `frontend/` | React app. | OpenAPI contract only |

**`core` and `api` must never import `sim` or `eval`.** Enforced by Maven module boundaries AND an ArchUnit test. Never "fix" a failing boundary test by moving code across it.

## 3. Evaluation integrity rules

1. The engine sees **observable** donor fields only (`DonorSnapshot`). Latent traits and true response probabilities live in `sim` and are visible only to `eval` (for ground truth and the oracle baseline).
2. Observable history statistics must be *derived from simulated past events*, never copied from a latent field.
3. **No hand-typed result numbers** anywhere (README, docs, paper tables). Results come from `lifeline-eval` CSVs; tables and figures are generated by scripts.
4. **Never weaken, delete, skip, or loosen a test to make it pass.** Fix the code, or report the failure.
5. Tuning seeds (1000+) are separate from reporting seeds (1-30). Never tune on reporting seeds.
6. Every simulation parameter is listed in `docs/PARAMETERS.md` with a source or the label `ASSUMPTION`. Do not invent citations, statistics, or population figures. Values in `docs/PARAMETERS.md` and `docs/population.yaml` are human-approved inputs: use them as given, do not change them. If a needed value is missing, add a row marked `TODO(human)` and stop; the build must fail on any `TODO(human)` under `src/main/resources/sim/` when experiments run.
7. Deviations from `docs/EVALUATION_PROTOCOL.md` after results are seen must be logged in `docs/DEVIATIONS.md`, not silently applied.
8. Report losses as well as wins.

## 4. Code conventions

- Immutable domain as Java `record`s; constructor injection; no static mutable state.
- All randomness via an injected `RandomGenerator` (`SplittableRandom`) seeded from config. Same seed + same config = identical output.
- Configuration in YAML; no magic numbers in factor code.
- Public engine API has Javadoc. Decisions logged at DEBUG with request id. No `System.out`.
- Tests: JUnit 5, AssertJ, jqwik (properties), ArchUnit (boundaries), Testcontainers PostgreSQL (api).
- Package by feature, e.g. `lifeline.core.factor`, `lifeline.core.rank`, `lifeline.core.explain`.

- Small commits with conventional messages (`feat:`, `test:`, `fix:`, `docs:`).
- Run `mvn -q verify` before declaring a phase done.
- If the spec is ambiguous or conflicts with section 1, stop and ask. Do not guess.
